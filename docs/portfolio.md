# morning-agent — 制作記録

> 作成日: 2026-03-25
> リポジトリ: morning-agent

---

## なぜ作ったか

毎朝スマートフォンを開いて、Gmail・Googleカレンダー・気になるニュースサイトを順番に巡回する習慣があった。これは10〜15分かかるうえ、情報が散在していて頭の整理がしにくい。

「今日やること」「返信すべきメール」「業界の動き」が一枚のメールにまとまって届いていれば、起きてすぐに今日の文脈を掴んで動き出せる。それが出発点だった。

加えて、Claude APIのtool_use（関数呼び出し）を実際のプロダクトで試してみたかったという技術的な動機も重なった。

---

## コンセプトと設計思想

### 「秘書ではなく、新聞」

最初のプロトタイプはLLMに「今日はどう動けばいいか教えて」と問いかける形だった。しかしそれでは毎朝の判断をAIに委ねすぎになる。

方向を転換し、**読者が自分で判断できるよう情報を整理して届ける**、新聞的なスタンスに落ち着いた。LLMの役割は「判断」ではなく「編集」である。

### エージェントを疎結合にする（ADR-002）

情報ソースは増減する。今は Calendar・Gmail・Webの3系統だが、将来的にNotion・RSS・Xなどが加わるかもしれない。そのため、各収集エージェントを `Agent` インターフェースで抽象化し、`pipeline.register()` の1行で追加・削除できる **Strategyパターン** を採用した。

収集層は `Promise.allSettled` で並列実行する。1つのエージェントが失敗しても他の結果を捨てない設計は、毎朝欠かさず動くツールには不可欠だった。

```
[collect phase: 並列]           [compose phase: 直列]
CalendarAgent ─┐
GmailAgent    ─┼── Pipeline ──→ ComposerAgent ──→ SES
WebAgent      ─┘
```

### サーバーレスで維持費ゼロ（ADR-001）

1日1〜2回の定時バッチにEC2やECS Fargateは過剰だ。AWS Lambda + EventBridge Schedulerなら、月間のAPI呼び出しが無料枠に収まり、常時起動コストもゼロになる。

実行時間の上限（15分）がトレードオフだが、情報収集・生成・送信を合わせても5分以内を非機能要件とすることで許容範囲に収めた。

### 観測基盤は最小限に（ADR-003）

LLMのトークン使用量とコストは把握したい。Langfuseなど専用の観測SaaSも検討したが、1ユーザー・1日数回の実行規模では導入コストが見合わない。加えて、GmailやCalendarの内容が外部SaaSに送信されることへの抵抗感もあった。

構造化JSONをCloudWatch Logsに出力し、Logs Insightsでクエリする自前実装を選択した。将来マルチユーザー展開の際にLangfuseへ移行しやすいよう、ログ構造はLangfuseのtraceモデルを参考にして設計した。

### 認証は一度だけ手動で（ADR-004）

個人Gmailにはサービスアカウントが使えない。OAuth2でrefresh_tokenを取得し、AWS Secrets Managerに保存する方式を採った。初回のみ手動操作が必要だが、それ以降はLambda起動のたびにaccess_tokenを自動更新するため、運用負荷はゼロだ。

## 開発の流れ

全工程が **約3日** で完結した。Claude Codeをペアプログラマーとして使い、ADRで事前に設計を固めてから実装に入ったことで、手戻りが少なかった。

| 日付 | 出来事 |
|------|--------|
| 2026-03-23 | ADRを書き、初版実装。Web検索・メール送信の動作確認まで完了 |
| 2026-03-23 | モデルをHaikuに切り替えてコスト削減。記事まとめを新聞レイアウトに変更 |
| 2026-03-24 | 日付ズレのバグ修正。収集フェーズと送信フェーズの分離。配信時刻を6:30に変更 |
| 2026-03-24 | AWSへのリリース完了。本番稼働開始 |
| 2026-03-25 | 夕刊便（18:00 JST）を追加。朝刊・夕刊の2便体制に |

### 印象に残った設計判断

**Claude Codeとの役割分担**
実装は「ADRでインターフェース定義 → Claude Codeに実装を依頼 → 動作確認 → 次のレイヤーへ」というサイクルで進めた。プロンプト集（ADRファイル内）を先に書いたことで、Claude Codeへの依頼が具体的になり、出力がぶれなかった。

**メール件名の変更**
「今日のブリーフ」という言葉が自分には少し硬く感じられたため「ピックアップ情報」に変更した。ツールの雰囲気はこういう細部で決まる。

**夕刊便の追加**
朝だけでなく夕方にも情報整理の需要があることに気づき、EventBridgeのcron設定を追加するだけで実現できた。疎結合な設計が活きた瞬間だった。

## 振り返り

**うまくいったこと**

- ADRを先に書いたことで、実装中に「なぜこう作ったか」を迷わなかった
- Strategyパターンによる疎結合が、夕刊便追加時に効果として現れた
- コスト管理をCDK + CloudWatch Logsの組み合わせで完結させ、外部依存を最小にできた

**次にやるとしたら**

- トピック設定をUIから変更できるようにしたい（今はyaml直編集）
- メール本文のパーソナライズ精度を上げるため、過去の開封率や反応をフィードバックループに組み込む
- 複数ユーザーへの展開時点でLangfuseを導入し、プロンプトのA/Bテストを行う

## 所感

「使えるものを3日で作る」という目標は達成できた。ADRという形式で設計の意図を文章に残しておくと、実装中・リリース後のどちらでも判断の根拠に立ち返れる。ツールを作ること自体より、**なぜこう作るのかを先に言語化する習慣**が、短期間でのリリースを支えたと思う。
