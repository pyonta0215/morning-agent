# 第2章 スキーマ契約 — 実験設計（確定版）

> 作成 2026-06-28。学習計画 第2章（6/29-7/10）の設計。第1章（評価工学）の成果物＝
> `scripts/eval.ts` と実行アーカイブ（S3 `archive/`）を流用する。
> 実装支援は可だが、記事・指標解釈・チューニングは学習者に残す方針。

## 1. 第1章 → 第2章 の接続（測る → 縛る）
第1章の最大の発見は「品質指標が飽和（ceiling）し、`description` 有無のナイーブA/Bでは差が
出ない」こと。よって第2章は**品質でなく「schema設計が出力の劣化（トピック崩壊）をどれだけ
防ぐか＝制約強度」**を測る。教材は 6/18 の実崩壊（commit `2ea062d`）。

## 2. 中心仮説
> **構造化出力は出力の「形」は強制するが「意味」は強制しない。
> しかし形の設計は意味に波及する（shape → semantics spillover）。**

- 旧schema（flat配列＋topicフィールド）: `ai`だけのitemsを返しても**形は妥当** → 6/18崩壊。
- 新schema（トピックID键・全required）: APIが全トピックキーの存在を保証。だが各キーは`[]`可。
  空配列を許しているのに、キーが並ぶことでモデルがトピックを埋める方向に動く——を定量化する。

副次的に「Anthropic `json_schema` 出力が"形"をどこまで強制するか（hard / best-effort）」も判明する。

## 3. 変数（schema強度を構造要素で分解）— V0/V1/V2 の3段階
| 変種 | 構造 | 键化 | 全網羅required | 分離できる効果 |
|---|---|---|---|---|
| **V0** 弱 | `{items:[{topic enum,...}]}` flat配列 | ✗ | ✗ | 崩壊版（pre-2ea062d 復元） |
| **V1** 中 | トピックID键オブジェクト・`required:[]` | ✓ | ✗（キー任意） | 「键化」単体の効果 |
| **V2** 強 | トピックID键＋全required（現行 `buildSummaryFormat`） | ✓ | ✓ | 「键化＋網羅」 |

V0/V1/V2 を比べることで「键化が効くのか／網羅requiredが効くのか」を分解できる。
（将来オプション V3 = V2＋`minItems:1`：候補無トピックに捏造を強いる＝**意味は縛れない証明**。今回は対象外）

### スキーマ定義（実装時の基準）
- 共通 itemSchema: `{url, title, summary, score:int enum[1..5]}`、全required、`additionalProperties:false`。
- V0: `{type:object, properties:{items:{type:array, items:{...item, topic:{enum:ids}}}}, required:[items]}`。
- V1: `{type:object, properties:{<id>:{type:array,items:itemSchema} …}, required:[], additionalProperties:false}`。
- V2: V1 と同形だが `required:[全id]`（＝現行 `buildSummaryFormat` をそのまま）。

## 4. 刺激（stimulus）= 実データ ＋ 敵対的合成入力
崩壊を確実に誘発して差を出すため、両方を入力に使う。

**(a) 実アーカイブ sources**（`runArchive` loaderで取得）
- 6/18（既知の崩壊日・ai偏重）、および通常日 数本（例 6/24・6/26・6/28）。

**(b) 敵対的合成 sources**（実データを加工して人工生成。ground-truthが既知）
- `ai偏重`: ai に大量スニペット（例 ×10）＋他トピック各1。← 6/18の構造を増幅。
- `全トピック大量`: 各トピック数件ずつ。単なる総量増で崩れるか。
- `薄い日`: 各トピック1件。空/救済の挙動確認。

合成入力は「どのトピックに候補があるか」を我々が把握しているので、崩壊判定の真値になる。

## 5. 測定（品質でなく崩壊率）
各 `(変種 × 入力)` を **K=10** 回繰り返す（temperatureは**本番デフォルトのまま**＝刺激は
敵対入力で作り、温度は本番忠実に保つ）。出力ごとに：

- **topicsCovered** = ≥1件で埋まったトピック数。
- **collapseRate(変種, 入力)** = `topicsCovered < (候補ありトピック数)` となった試行の割合。
  - 合成入力では候補ありトピック数が既知。実データは**同一入力上での変種間相対比較**で評価
    （V2が5/5・V0が1/5 等）＋ sources非空をフロアに使う（絶対真値の曖昧さを回避）。
- **per-topic fillRate** = 各トピックが非空だった試行割合（どのトピックが落ちやすいか）。
- **shapeViolation率** = schema形自体の違反（strictなら0のはず＝「形は守る」の確認材料）。

期待：V0 は崩壊率高（特に ai偏重 と 6/18）、V2 ≈ 0。V1 が中間なら「键化 vs 網羅」を分解できる。

## 6. 実装計画（本番非干渉）
**webAgent.ts は触らない**（web_searchを7/5まで観測中のため凍結）。実験は独立スクリプト：

- `scripts/ch2-schema-eval.ts`（新規）
  - `runArchive` の loader で実 sources をロード（eval.ts と同じ .env AWSキー削除＋defaultプロファイル）。
  - 合成 sources ジェネレータ（実データ加工）。
  - 集約呼び出しを複製（webAgent.ts run() の summaryResponse 相当・~25行）。schema は V0/V1/V2 を切替。
  - 崩壊判定＋集計＋レポート（eval.ts のテーブル様式流用）。結果を `eval-results/` にJSON保存。
- 本番の集約を将来テスタブルにしたければ、7/5以降に `aggregate()` 切り出しを別途検討。

## 7. コスト（K=1スモークで実測補正）
Haiku集約は **実測 ~$0.032/call**（sourcesが大きく 入力~11.5k・出力~4k tok/call。当初の$0.003は過小だった）。
3変種 ×（実3＋合成3）× K = 18K call。**K=6 ≈ 108 call ≈ ~$3.5 / K=10 ≈ 180 call ≈ ~$5.8**。

## 7b. K=1スモーク結果（2026-06-29・予備・n=1）
`scripts/ch2-schema-eval.ts --k 1`（$0.58）。**仮説が予備的に支持された**:
- 実データ（6/18・6/28・6/29）と synth:all-heavy では全変種 崩壊率0%（材料が十分なら schema 差は出ない）。
- **synth:ai-flood（ai:8・他1）と synth:thin（各1）で V0/V1 が `finance` を脱落（崩壊率100%）、V2 のみ全網羅（finance:100%）**。
- ⇒ 効くのは「键化」ではなく「**全required（網羅強制）**」。V1（键化のみ・required無し）は V0 同様に崩壊した。
- ⇒ schema契約の効果は「薄い/支配されたトピック」という**ストレス下でのみ顕在化**。健康な実データでは現れない。
- 注: n=1。**K=5で補正したところ V2は常時4/4ではなかった（下記7c）。K=1は小標本の偶然**。

## 7c. K=5 確定結果（2026-06-29・差が出る2入力に限定・$0.65）
`--inputs ai-flood,thin --k 5`。候補トピックは実質 `finance`（薄い/支配されるトピック。`game`は
6/18 donor の単一ソースが抽出不能で全変種0＝候補から除外され、勝負は finance の保持率に集約）。

| 入力 | 変種 | 崩壊率 | finance fill率 |
|---|---|---|---|
| ai-flood | v0 | 80% | 20% |
| ai-flood | v1 | 100% | 0% |
| ai-flood | **v2** | **40%** | **60%** |
| thin | v0 | 100% | 0% |
| thin | v1 | 60% | 40% |
| thin | **v2** | **40%** | **60%** |

**確定した読み（K=1の楽観を補正）**:
1. **V2（全required）が最も頑健**：両入力で崩壊率最小(40%)・finance保持最高(60%)。schema強度の効果は実在。
2. **だが V2 でも崩壊は消えない（40%）**：required はキーの存在を保証するが、モデルは `finance:[]` を
   返せる。⇒ **中心仮説の最もクリーンな実証＝「構造化出力は"形"(キー存在)は強制するが"意味"(非空)は強制しない」**。
   schema契約は意味への"ナッジ"であって"保証"ではない。
3. **V0 vs V1 の分離は n=5 ではノイズ大**（ai-floodではv0<v1、thinではv0>v1）。「键化単体の効果」は
   この標本では結論不可。誤差棒が広い。
4. ⇒ 第2章の主張は「schema強度↑で崩壊↓（V2が最良）。ただし shape は semantics を保証しない（V2も40%崩壊）」。
   V0/V1分解やrate確定にはKを上げる必要（コスト判断は学習者）。

## 8. 成果物（第2章の記事）
「構造化出力は"形"の契約であって"意味"の契約ではない。だが形の設計は意味に波及する」を
